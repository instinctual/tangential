2. About this document
This document is the current release of the control unification system from Tangent that enables a
standard protocol to communicate with all panels manufactured by Tangent regardless of physical
connection type (USB, Ethernet etc.)

This document is designed to form a base specification for the various elements that make up the
system. This should enable all parties to start work on their components. It is however certainly not
the final iteration and may be extended and enhanced as required.

Some terms used throughout this document:
  • partner – you, the Software Manufacturer.
  • application – your software application.
  • software-control – a control / value inside the application.
  • physical-control – an actual control on a panel (knob, button, trackerball).
   • encoder – knobs and trackerballs are both treated as encoders by the software.
            When the word encoder is used it refers to either type of physical controls.
   • Mapper – the tool supplied to allow users to customise their panel layouts
   • Hub – the background process which provides the bridge between your application and the
      tangent panels.

Throughout the document references are made to the Element panels. These are the next
generation of panels from Tangent.


3. Introduction
The Tangent Unified Bridge Engine (TUBE) is made up of two software elements, the Mapper and
the Hub. The Hub communicates with your application via the TUBE Inter Process
Communications (TIPC) protocol. While it is important to understand the role that each element
plays in the overall system this document will concentrate on the TIPC protocol.

TIPC is a standardised protocol to allow any application that supports it to communicate with any
current and future panels produced by Tangent via the TUBE Hub.

The aims of TUBE are:
   • Partners need only write code just once to support any Tangent panel. This reduces the
       work required by partners to support current, historic and future panels.
   • Users can customise how the panels operate with their applications through the TUBE
       Mapper’s graphical interface. This customisation tool is available to download free of
       charge so there is no need for our partners to write their own customisation tools.
   • Users can choose which panel or combination of panels they want to use with their
       application, even combining panels from different ranges.
   • There’s no need for partners to understand or deal with different communication protocols
       or hardware interfaces and drivers (USB, Ethernet etc.) – this is all handled by TUBE.
   • Applications no longer need to drive panel displays, this is all handled by the Hub.
   • TIPC uses simple inter-process communication via sockets.
   • Multi-platform support: Windows, Linux, Mac OS X.
   • Partners gain instant access to any new Tangent panel types and features (a good
       example of this is touch surfaces like our iPad app).
   • As partners add features to their application they can quickly map these to panels for in-
       house testing and subsequent release without waiting for Tangent to do anything.

4. Overview
The following diagram is an overview of the TUBE system:




The components of the system as follows:
   • Application: your application.
   • Hub: this is a background process that acts as the bridge between your application and the
      panels using the various communication protocols (USB, Ethernet etc.). It is the
      responsibility of the Hub to handle the mapping of the software-controls to the physical-
      controls (using the XML files) and any commands and responses to / from the panels.
   • Mapper: this is a utility which we supply that allows the user to customise the way the

   • Controls XML: this is an XML file that describes all the controls that the application has
      which a panel can control. Tangent can help by writing this for you, but we would need a list
      of all the controls etc.
   • Default Map XML: this is the default (or factory supplied) layout of how the panels work
      with the application. The user will use this as the starting point for their own custom Map
      files. While Tangent can help by generating the Default Map for you it would make more
      sense for you to supply this yourself; you understand far better than us how users work with
      the application. You can use the Mapper to create this.

   •   User’s Custom Map XML: the user can save various custom mappings, choosing the way

4.1. Abstraction of controls
The Hub abstracts the application from the panels. The application need not know what type of
panel is sending the information and how it’s sent. The application also does not need to know
what physical-control on the panel is mapped to which software-control in the application at any
time as this is handled by the Hub. The application just gets told that changes to make to software-
controls. This means the Hub has to know what software-controls are available and how to identify
these to the application. This is described in the Controls XML file.

The Map XML files define which particular physical-control is mapped to which software-control at
any one time depending on the current Mode & Bank selections (more on Modes and Banks in
Sections 8 and 9). This enables the Hub to convert physical-control movements into software-
control changes and software-control changes into panel display updates.

So, as an example, let’s say we move encoder 3 on the panel. The Hub looks at the selected Map
XML file and sees that encoder 3 is mapped to parameter C. The Hub then reports to the
application that parameter C has changed by a given amount.

To continue the example, if the application changes parameter C, then the application reports to
the Hub that the parameter C has a new value. The Hub looks at the selected Map XML file to find
out which, if any, encoder is currently assigned to that control. The Hub then updates the display
next to encoder 1 on the panel.

The above example is very simplistic but it shows that the application doesn’t need to know
anything about panels that may be connected.

Some applications may not want to use the abstraction layer provided by the Hub. For such
applications there are a number of commands which enable (almost) direct communication with the
panels. This is known as Unmanaged Mode– see Section 5.

5. Unmanaged Mode
This feature enables applications to communicate with panels at a low level, bypassing all the
abstraction features provided by the Hub. Use of this mode is not recommended as all the user
mapping advantages provided by the Hub will no longer apply. However, if an application has very
specific needs which are not met by the regular, managed, mode then this is a solution which still
provides the application switching benefits of the Hub.

To enable Unmanaged Mode the application indicates this in its ApplicationDefinition command
which is the first command it sends to the Hub. As no XML files are required when running in this
mode the switch is indicated by passing a zero length value for the system directory string.

Once this mode is enabled the Hub will send ‘unmanaged’ commands to the application which
indicate control movements. The application can also send text to be shown on the panels’
displays using the ‘unmanaged’ command.


6. Panel Emulation Options
The Tangent software includes an option for the new Ripple panels to emulate element-Tk panels
if required. This allows Ripples to be used out-of-the-box with any software that currently only
supports element panels. If emulation is not required the Ripple panel can be used as a normal
individual panel. Panel emulation is available for both managed and unmanaged applications.

The option is selected via the Tangent Mapper (section 13) control map settings menu and is set
per application. If emulation is active, the Ripple panel will appear to the application as if it was a
standard element-Tk and use any control mappings set on the element-Tk. If not active, the panel
appears as a standard Ripple panel with its own set of control mappings.

There is a default setting for the Ripple to element-Tk emulation for each application that is derived
from the current mapping set-up for that particular application. The user can override the default
setting at any time and choose to either have the Ripple appear as an element-Tk, or as a
standard Ripple panel.

For managed applications, the default is decided by the presence (or not) of a default map file for
the Ripple panel type as discussed in section 12.1. If an application supplies a default map file for
Ripple panels, it is assumed that the Ripple panel is fully supported by the application and no
emulation is required. If a managed application doesn’t supply default mapping data for Ripple
panels, the emulation is switched on by default to allow Ripple panels to be used out-of-the-box
with any software that currently only supports element panels.

As a developer, you may want to fully support the Ripple panel in your managed application by
supplying a default control map for this panel type. If you don’t, you can fall back to using panel
emulation to allow Ripple panels to share the default mappings for element-Tk panels. The user
can always change the emulation setting later and create their own Ripple panel map (for
managed applications only).

All unmanaged applications are currently assumed to want Ripple to element-Tk panel emulation
to be active unless a Tangent update or a user setting decides otherwise. If your unmanaged
application will have full support for the new Ripple panel, please contact Tangent and we can
update the default emulation setting for your particular application.

7. TIPC
TIPC communication is bi-directional:
      software-control change requests and actions travel from the Hub to the application.
      software-control and Mode changes travel from the application to the Hub.

The Hub is a background process running on the host platform. The application communicates with
the Hub via streaming TCP/IP sockets. See Section 14 Inter Process Communication Sockets
for the procedure to initiate communications.


7.1. Software-control data types
When the Hub communicates with your application there are three ‘classes’ that the software-
controls can be grouped into. These are types of control relating to the application rather than
physical-controls (like knobs or buttons) which are the data types that the panels use to
communicate with the Hub.

These are:
   • Parameters: Software-controls which have a wide range of values that would normally be
      controlled by a slider on the GUI or a knob / trackerball on a panel.

   •   Menus: Software-controls with a limited number of possible states that would normally be
       presented to the user as a menu on a GUI. Even something which has only two states like
       ON or OFF is treated as a menu. A menu can be controlled by a button – pressing it to step
       to the previous / next item, or a knob – turning it to select the previous / next item. The hub
       does not know all the possible “values” of a menu, it only holds the text label for the current
       menu item that is selected.

   •   Actions: This is specific command that has no value and would normally be associated
       with a button on the GUI or panel. Examples of typical actions are ADD_MARK,
       NEXT_CLIP, ENABLE_BYPASS and transport type commands such as PLAY_FWD,
       INCH_REV, STOP etc.

Standard parameters, menus and actions are predefined by a controls XML file and they are
referred to by a unique and preset numerical identifier. The latest version of TIPC extends this to
support custom controls for each type which are referred to by string identifiers that can be passed
from application plug-ins that may wish to add extra controls. Every command that handles a
standard control has a corresponding custom control version. The format of the commands and
their use are the same for both implementations with the only difference being the standard version
passing a numerical id and the custom version containing a string id instead. Both types of control
id commands may be used together by an application so the standard set of predefined controls
can be extended by the use of custom controls. Custom control support must be enabled in the
controls file with the addition of the CustomControls capability node.

Now that we understand about data types we can look at the commands that TIPC provides to
communicate information about these between the application and the Hub.

commands can be grouped together into a single message which starts with the number of bytes

7.3. Command overview
Commands can be split into two groups based on the direction of flow: (1) Commands from the
Hub to the application and (2) Commands from the application to the Hub.

The format for each command listed here is given in Section 15 TIPC protocol format.

7.3.1. Commands from the Hub to the application

•   InitiateComms: Once a socket connection has been established, this initiates the
    communication between the Hub and the application. The number and type of panels
    connected are detailed so that the application may make use of this information if applicable.

    The application should then reply with an ApplicationDefinition command and a ModeValue
    command.

•   ParameterChange: This is used to ask the application to change a parameter and is sent in
    response to a user moving a knob or trackerball which is currently mapped to control that
    parameter. Note that a relative increment / decrement is sent and not an absolute value. On
    receipt, the application will need to apply this offset to its internal value and respond to the Hub
    with            the              corresponding                ParameterValue              command.

    If the parameter has already hit its maximum or minimum value and this change request has no
    effect    then   there    is   no     need   to   return  a    ParameterValue     command.

•   ParameterReset: This is used to tell the application that the user has pressed the reset button
    for a given parameter. Knobs and both axes of a trackerball have a reset button associated
    with them. Note there is no value or data associated with this. The application needs to decide
    what value to set the parameter to when this command is received.

•   ParameterValueRequest: This is used to ask the application for the particular value of a given
    parameter. This is typically used after an AllChange has been sent by the application and the
    Hub needs to know the values of all the parameters a panel is controlling so it can display
    them.

•   MenuChange: This is used to ask the application to change a menu to the previous or next
    item. This is sent in response to a user moving knob or pressing a button that is controlling a
    menu. The only data / value associated with this is +1 for next or -1 for previous. On receipt,
    the application should respond to the Hub with the new menu value using the MenuString
    command. If the menu has no further values in the direction that is requested and this change
    request has no effect then there is no need to return a MenuString command.

•   MenuReset: This is used to tell the application that the user has pressed the reset button for a
    given menu. The application should apply the reset value and respond to the Hub with the new
    menu value using the MenuString command.


                                                                                              13
                                                             TUBE Version 3.12 - TIPC Rev 9


•   MenuStringRequest: This is used to ask the application for the text label of the current menu
    item that is selected This is typically used after an AllChange has been sent by the application
    and the Hub needs to know the “values” for all the menus a panel is controlling so they can be
    displayed.

•   ActionOn: This is used to tell the application that a given action needs to be acted on.
    Typically this is in response to a user pressing a button, for example PLAY. There are no
    values associated with this command.

•   ActionOff: This is used to tell the application that a given action needs to be acted released.
    Typically this is in response to a user releasing a button, for example STOP. There are no
    values associated with this command. Together with the Action On command this can be used
    to enable the Application to perform different (but hopefully closely related!) actions when a
    combination of buttons are held down together.

•   ModeChange: This is used to tell the application that the mode has changed. This is normally
    in response to the user having pressed a button. Modes are explained later.

•   Transport: In addition to transport functions that can be conveyed as actions there are specific
    Jog / Shuttle functions may be sent by this command. The hub manages the Jog / Shuttle
    status and the sensitivity control of the Transport Ring parameter and will report movements of
    the control accordingly.

•   UnmanagedPanelCapabilities: This is sent in response to a UnmanagedPanel-
    CapabilitiesRequest command. It is used to inform the application of the number of controls
    and displays which a panel has. This is only relevant for applications which are driving the
    panels in Unmanaged mode.

•   UnmanagedButtonDown: When a panel is in Unmanaged mode this is sent whenever a
    button is pressed.

•   UnmanagedButtonUp: When a panel is in Unmanaged mode this is sent whenever a button is
    released.

    encoder is moved. Encoders include both Knobs and the individual axes of trackerballs.

7.3.4. A note on Menu Commands
The strategy for menu commands gives a simple interface that will hopefully fit the majority of
circumstances without causing too much work. Alternative strategies have been considered which
may be more flexible but which may also cause significant additional coding effort. It is uncertain
how many menu controls each application is likely to have and consequently it is difficult to
ascertain how much effort should be devoted to the Menu interface on both sides.

The pros and cons of each strategy are outlined here:

Relative control
This is the method described above in Section 7.3 Command overview.

Pros:
   • There’s no need to define all menu items within the Controls XML file.
   • The introduction of new menu items will not require the Controls XML file to be updated.

Cons:
   • The application must have access to the text representing the menu items to transmit to the
      TUBE Hub on demand.
   • There is no ability to display menu item text of a length appropriate to the physical panel
      connected.
   • It will not be possible to display anything but the currently chosen menu item text at any
      time.

Absolute control
This is an alternative option

The pros and cons are the inverse of the relative control method:
Pros:
   • The application need not have access to the text representing the menu items at run time.
   • There is the option of displaying menu item text of a length appropriate to the physical
       panel connected.
   • On appropriate panels (e.g. the vWave iPad app) drop-down menus can show all the menu
       items, as on a conventional GUI.

Cons:
   • All menu items must be defined within the Controls XML file.
   • If text lengths appropriate to each panel type are to be available then these will need to be
      defined in the Controls XML file..
   • The introduction of new menu items will require the Controls XML file to be updated.

If there is sufficient demand for Absolute Control to be included then this will be added as
extension commands at a later date.

8. Modes
Now is a good time to talk about modes as we’ve mentioned them in the commands and they are
referred to in the Sections 11 Controls XML and 12 Map XML.

A mode is a way of grouping software-controls that are associated with a particular process. A
good example would be creating a secondary isolation, where several parameters are involved in
doing this, for example hue centre, hue spread and hue softness etc. Telling the Hub that
secondary isolation has been selected as the current mode on the GUI would allow the Hub to
update the panel to show those software-controls associated with secondary isolation.

Modes are defined in Controls XML which just lists the different modes, a unique identifier for each
and a text label for it. The controls that are actually in each mode are defined in the Map XML files.

It may be that the application does not have any notion of modes – all software-controls may be
“live” at the same time and the user does not need to switch mode on the GUI in order to do a
secondary isolation. In this case the application would never send the ModeChange command or
respond to receiving a ModeChange command.

However, even if the application does not have the notion of modes, it would still be useful for
modes to exist for the panel as it will help the user to group controls into logical blocks in the Map
XML file. This is for two reasons:
  • The controls are presented to the user in the Mapper in modes.
  • The user may select the mode from the panel so that only the controls that are relevant to
       the current process they are doing are controlled and displayed by the panel.

Even if you decide not to implement multiple modes there must be at least one mode as all
controls must be defined within a mode.

                                                           TUBE Version 3.12 - TIPC Rev 9

9. Banks
Another subject to talk about before we look at the Controls XML and Map XML Sections is
banks.

We’ve covered the idea of modes and seen how they allow us to group software-controls together
which are part of a particular process or mode of working. It is possible that within any mode there
may be more software-controls associated with it than there are physical-controls on a panel.

This is where banks come in. A bank is just a collection of knobs or buttons that you want to
display together at the same time. If more knobs and buttons are required than a panel has
physical-controls for in one go you can simply add another bank. You step through the banks using
buttons on the panel.

So, within each mode there may be several banks of software-controls.

It obviously makes sense where there are several banks within a mode that the software-controls
within each bank are also grouped logically – just as you would logically group the software-
controls within each mode.

Each mode obviously has to have at least one bank.

It should be noted that trackerballs, knobs and buttons each have their own banks which operate
independently of each other. So, for example, if you add a new bank of knobs then that new bank
is only added for knobs. If a mode previously had four knob banks, four buttons banks and one
trackerball banks, then after adding an extra knob bank you would have five knob banks, four
button banks and two trackerball banks.

Under ‘normal’ circumstances stepping through a particular type of bank (e.g. button banks) will
cause all controls of that type to change, regardless of what panel they appear on. This allows a
single button to change banks on multiple panels. However, sometimes this is not the best way to
operate and this can be overridden so that a bank change action will only apply to the panel from
which the action was fired i.e. the next bank button pressed. See Section 11.1.2 for details of how
to set this behaviour.

Finally, there are a subset of hardware-controls that do not appear in any bank. These are controls
that have no associated display and should therefore not change function when changing bank.
Normally these would be buttons with printed legends and trackerballs that have no display.

While it is important for you to understand the concept behind the grouping of controls into banks
the application will have no knowledge of banks; whether they exist or which bank is selected.
Banks are purely a TUBE and panel concept.

10. The ALT key
Another way for users to map extra functionality to physical-controls is to define an alternative
function which is applied when the ALT key is held down on a panel. This could be a different
sensitivity for the same software-control (parameters only) or a completely different function
altogether.

As with banks above the application has no knowledge of whether the ALT key is held or not, it is
purely a TUBE and panel concept.

12. Map XML
The Map XML files describe which software-controls appear within each mode and which physical-
control on the panel they are mapped to in that mode. They also describes how the software-
controls are further broken down into banks where required.

There are two types of Map XML files; Default and User.

Map XML files are normally generated using the Mapper utility however, as they are XML files they
can also be generated by hand. The Mapper has shortcuts to copy functionality between modes
and banks however, when hand coding the files, this will unfortunately need to be done manually.


12.1. Default Map XML
These files define the recommended layout for an individual panel. The user is likely to use the
layout created by this file as the starting point for their own custom layout, adding new banks or
adding software-controls to existing banks to suit their own preferred way of working.

As Tangent offer several different panel ranges and models it is strongly recommended that a
Default Map XML file is supplied for each panel model available. If the file exists then, when a user
connects that panel model for the first time, some control mappings will appear. If the file does not
exist then the panel will initially appear blank and the user will be forced to generate their own
mapping before they can use the panel at all.

Note that the user will not be able to delete or alter any Default Map XML files. They will only be
able to save and alter a copy of the file. This means for support issues you can always ask the
user to revert to a known and approved configuration.

12.3. Multiple panels of the same type
The Hub can handle multiple panels of the same type to be attached at the same time. This allows
the configuration to be infinitely expanded to have any number of controls. Under these
circumstances the Map files may optionally supply multiple mappings and identify which panel
number they are to be applied to. By number we mean a value which uniquely identifies a panel
so that panels of the same type can have the correct mapping applied to each.

For example: You may wish to configure the Hub to expect two Element-Bt panels to be
connected. In the Mapper, each of these two panels would be identified by a number tag which is
associated with the panel’s Serial Number. The number tags for these panels would be 1 and 2.
When the map files (either system defined default or user generated custom) are loaded, the Hub
first searches for a panel mapping with a number attribute which corresponds to the panel in
question. If no such mapping exists then the generic mapping, with no number tag, is loaded from
the map file.

14. Inter Process Communication Sockets

Communication between the application and the Hub is via streaming TCP/IP sockets. The hub
should always be running as a background process and listening for a connection on port 64246.

To open a communication socket to the Hub the application could use code similar to the following.
Other than the first two lines the code is almost the same for all platforms.


typedef SOCKET Socket        <- Use for Windows
typedef int Socket           <- Use for OSX and Linux

Socket               socketHandle;
struct sockaddr_in   address;


// create the socket
socketHandle = socket(PF_INET, SOCK_STREAM, IPPROTO_TCP);
if (socketHandle == -1)
{
    // create socket failed
    exit(0);
}

// prepare the address
memset(&address, 0, sizeof(address));
address.sin_len = sizeof(address);      <- Only needed for OSX
address.sin_family = AF_INET;
address.sin_port = htons(64246);
address.sin_addr.s_addr = htonl(INADDR_LOOPBACK);

// connect to the hub
if (connect(socketHandle, (struct sockaddr *) &address, sizeof(address)) == -1)
{
    // connect failed
    exit(0);
}

Once the application has established a socket connection, message passing is handled by reading
and writing data from and to the socket. You will be provided with some platform independent
sample code to assist with this.

The Hub then initiates communication by sending an InitiateComms (0x01) command to the
application.

15. TIPC protocol format
As explained above messages encapsulate a number of commands. Each message starts with a
32 bit integer value which indicates the number of bytes that will follow to complete the message.
Commands then follow one by one until the message is complete.

Format:           <numBytes>, <command1>, <command2>, …

Commands passed between the Application and the Hub all start with a 32 bit command ID with
the content and length defined by the command itself.


15.1. Data Types
The byte order for each data type is defined by the host platform’s hardware. As TIPC comms
always remain within one host platform there will never be any conflict between the sender and
receiver packing and unpacking the data in different ways. This allows the programmer to copy
bytes that make up a value from memory to the data stream (and vice versa) without worrying
about the endianness of the underlying hardware.

The same is true for floating point values. Bytes should be copied directly from storage memory
into the data stream and back in the same order. This avoids the need to manipulate the data
depending on the endianness of the underlying hardware.

Unsigned Int
A 32 bit unsigned integer value.

Signed Int
A 32 bit signed integer value.

Float
A 32 bit signed floating point value.

Bool
A particular type of Unsigned Int which is restricted to a value of 1 or 0, indicating True or False
respectively.

Character String
A sequence of characters represented by single byte values based on ASCII.
Strings are not null terminated.
Their maximum length is defined in the command.
See Section 16 Character Table for valid characters.

Path String
A special instance of a Character String which indicates the absolute path of a directory folder.
